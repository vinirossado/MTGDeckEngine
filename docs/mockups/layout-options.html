Graph Explorer — Layout Options

Three takes on the same MVP scope (visual graph + faster SPARQL + schema browsing). Same feature set, different priorities about which one dominates the screen. Each mock uses the MTGDeckEngine Xyris dataset.

Layout A — “Studio” recommended starting point

IDE-style. Schema browser left · editor+results center · click-to-inspect right. Closest to what a daily SPARQL workflow looks like in DataGrip/Stardog Studio.

Pros
  • Graph-first — the killer "wow, I can see my data" moment is the default view
  • Great for explaining RDF to someone new (the picture is the explanation)
  • Smaller surface area to build (one big canvas vs three panels)
Cons
  • Worse for daily querying — editor is just a one-liner, no syntax highlighting in a single input
  • Schema browsing is implicit (you discover by clicking) rather than explicit
  • Floating panels get messy with multiple selections

Layout C — “Lessons”

Notebook-style. Each "lesson" is a cell with prose + SPARQL + result. Schema appears as a chip strip per cell, not a sidebar. Optimised for learning paths and shareable demos.

Named graphs scope your data
Each commander's EDHREC stats live in their own named graph. This means you can ask "Xyris-specific inclusion" without affecting global card data.
▶ Cell 3.1 · count triples in the commander context GRAPH COUNT
SELECT (COUNT(*) AS ?n) WHERE { GRAPH <…/context/xyris-the-writhing-storm> { ?s ?p ?o } }
→ 1,247 scoped to the commander context
▶ Cell 3.2 · join named-graph signals with global card data GRAPH OPTIONAL FILTER
SELECT ?name ?syn WHERE { GRAPH <…/xyris> { ?card mtg:hasSynergyScore ?syn } ?card mtg:hasName ?name . FILTER(?syn > 0.5) }
2 rows Impact Tremors · Windfall view as graph
Pros
  • Pedagogical by default — perfect for "learning RDF" focus
  • Each cell tells you why, not just what
  • Shareable: commit the .sparqlbook file, anyone can run it
Cons
  • Friction for ad-hoc daily querying (must create a cell every time)
  • Far from what RDF engineers expect — less obvious upgrade path to "power user mode"
  • Graph visualization is a secondary action, not central
My recommendation: start with Layout A (Studio), but add Explorer's graph-view as a first-class results tab (already shown).

Reasoning: A serves the daily workflow (write query, see result, inspect) and gives you a clean home for the schema browser. The graph view lives there as a tab — you get the "wow" moment of Explorer without losing the IDE ergonomics. Lessons C is fantastic but is really a different product category (think Observable for graphs); could come later as a "notebook mode" toggle.
