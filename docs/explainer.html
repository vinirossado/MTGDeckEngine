MTG Deck Intelligence Engine

A .NET 10 knowledge-graph engine that fuses Magic: The Gathering data from EDHREC, EDHTop16, TopDeck.gg, and Scryfall into a single RDF triplestore — then answers questions no individual source can. Deep focus: how a knowledge graph changes the kind of question you can ask of a dataset.

What problem this solves

If you play Commander (the most popular MTG format), you have access to two great free data sources:

EDHREC

Tells you what's popular: "78% of Xyris decks play Windfall." Sourced from millions of community decklists.

EDHTop16 + TopDeck.gg

Tells you what wins: "This deck list went Top 4 in a cEDH tournament last weekend." Sourced from tournament organisers.

Those are different signals. A card can be popular but never win (precon staple). A card can win but be unknown (new tech). Neither source can answer the fused question on its own:

"Which cards appear in Top-4 Xyris decks, cost under €5, and are popular enough to swap into my casual build?"

This engine ingests both — and Scryfall for prices — into a knowledge graph and exposes a single API that answers questions across all of them.

RDF, in one screen

RDF (Resource Description Framework) is just data written as three-part statements: subject → predicate → object. Each statement is called a triple.

mtg:card/windfall
→
mtg:hasPriceEur
→
"4.88"

Three triples about Windfall in our store:

mtg:card/08becc07-…  a             mtg:Card .
mtg:card/08becc07-…  mtg:hasName     "Windfall" .
mtg:card/08becc07-…  mtg:hasPriceEur "4.88"^^xsd:decimal .

Notice three things:

  1. The subject is a URI. That URI is global — anyone in the world can point at the same Windfall.
  2. The predicate is also a URI. mtg:hasName means something specific (defined in our ontology), not just a string label.
  3. The object can be a URI (linking to another resource) or a literal (a string, number, date — typed via XSD).

From those three rules, a few things follow that make RDF different from SQL:

It's a graph, not a table

Every triple is an edge. Cards link to colours, decks link to cards, entries link to tournaments. You traverse by name, not by JOIN ON.

It's mergeable

Two datasets that use the same URI for Windfall combine for free. No FK reconciliation, no ETL. That's why this engine can fuse EDHREC, EDHTop16, and TopDeck without a matching step — they all key on Scryfall's oracle_id.

It's schema-flexible

Add a new predicate (e.g. mtg:hasTournamentWinRate) and old data still works. No ALTER TABLE, no migration. Phase 2 added 9 new predicates without touching Phase 1 code.

It speaks SPARQL

The query language for RDF. Like SQL but you match graph patterns instead of joining tables.

The SPARQL query that answers the DoD

"Cards in Top-4 Xyris decks under €5" becomes:

PREFIX mtg: <http://example.org/mtg#>

SELECT ?name ?priceEur (COUNT(DISTINCT ?deck) AS ?numDecks) WHERE {
  ?entry mtg:inTournament ?t ;
         mtg:hasPlacement ?placement ;
         mtg:hasDeck       ?deck .
  ?deck  mtg:hasCommander  mtg:commander/xyris-the-writhing-storm ;
         mtg:containsCard  ?card .
  ?card  mtg:hasName       ?name .
  OPTIONAL { ?card mtg:hasPriceEur ?priceEur }
  FILTER (?placement <= 4)
  FILTER (!BOUND(?priceEur) || ?priceEur <= 5.0)
}
GROUP BY ?name ?priceEur
ORDER BY DESC(?numDecks) ?priceEur
LIMIT 25

Read it top-down like a sentence: "Find me every tournament entry in a tournament that has a placement and a deck, where that deck has Xyris as its commander and contains a card. The card has a name and maybe a price. Filter to top-4 and under €5. Count distinct decks per card."

You couldn't write that against EDHREC or EDHTop16 alone — neither knows the other's data. In a knowledge graph it's one query.

The ontology — our schema in OWL

An ontology is the schema for an RDF dataset. It defines the classes, the predicates, and how they fit together. Ours lives in src/MtgDeckEngine.Ontology/mtg-ontology.ttl and looks like:

# Classes
mtg:Card            a owl:Class .
mtg:Commander       a owl:Class ; rdfs:subClassOf mtg:Card .
mtg:Deck            a owl:Class .
mtg:Tournament      a owl:Class .
mtg:TournamentEntry a owl:Class .
mtg:Color           a owl:Class .
mtg:Category        a owl:Class .

# A handful of predicates
mtg:hasName            a owl:DatatypeProperty ; rdfs:range xsd:string .
mtg:hasOracleId        a owl:DatatypeProperty ; rdfs:range xsd:string .
mtg:hasPriceEur        a owl:DatatypeProperty ; rdfs:range xsd:decimal .
mtg:containsCard       a owl:ObjectProperty   ; rdfs:domain mtg:Deck ; rdfs:range mtg:Card .
mtg:hasCommander       a owl:ObjectProperty   ; rdfs:domain mtg:Deck ; rdfs:range mtg:Commander .
mtg:inTournament       a owl:ObjectProperty   ; rdfs:domain mtg:TournamentEntry ; rdfs:range mtg:Tournament .
mtg:hasPlacement       a owl:DatatypeProperty ; rdfs:domain mtg:TournamentEntry ; rdfs:range xsd:integer .

# Phase 2 additions — never touched the Phase 1 classes
mtg:hasTournamentEntryCount   a owl:DatatypeProperty ; rdfs:domain mtg:Commander ; rdfs:range xsd:integer .
mtg:hasTournamentTopCutCount  a owl:DatatypeProperty ; rdfs:domain mtg:Commander ; rdfs:range xsd:integer .
mtg:hasTournamentWinRate      a owl:DatatypeProperty ; rdfs:domain mtg:Commander ; rdfs:range xsd:decimal .

# Phase 3 generalisation — hasFormat works on Tournament and Deck
mtg:hasFormat          a owl:DatatypeProperty ; rdfs:range xsd:string .

OWL gives you open-world semantics: missing data isn't false, just unknown. This is the opposite of SQL's closed-world model. It matches how messy real-world data behaves (EDHTop16 has prices in USD, TopDeck has them in EUR-ish, Scryfall has both — sometimes).

Named graphs — scoping data without losing the join

A subtlety: EDHREC's "78% inclusion" is true for Xyris specifically, not in general. So we don't write mtg:card/windfall mtg:hasInclusionPct "78" globally — that would lose the context.

Instead we use named graphs: a way of grouping triples under a context URI. EDHREC data for Xyris lives in mtg:context/xyris-the-writhing-storm.

# Global card data — default graph
mtg:card/windfall  mtg:hasName     "Windfall" ;
                   mtg:hasPriceEur "4.88" .

# Xyris-scoped EDHREC signal — named graph
GRAPH mtg:context/xyris-the-writhing-storm {
    mtg:card/windfall  mtg:hasInclusionPct "63.1" ;
                       mtg:hasSynergyScore "0.54" .
}

Queries can mix-and-match: "inclusion% from Xyris's context, price from the default graph". Same Windfall URI on both sides — joins for free.

SHACL — validating before write

OWL describes what data can exist. SHACL describes what data must. It's like CHECK constraints for graphs.

mtg:CardShape a sh:NodeShape ;
    sh:targetClass mtg:Card ;
    sh:property [
        sh:path mtg:hasOracleId ;
        sh:minCount 1 ;
        sh:datatype xsd:string ;
        sh:message "Card must have a Scryfall oracle ID."
    ] ;
    sh:property [
        sh:path mtg:hasName ;
        sh:minCount 1 ;
        sh:datatype xsd:string
    ] .

Before any graph is written, we run it through ShaclValidator: non-conforming triples raise ShaclValidationException with a full report. This catches structural bugs at the ingestion boundary instead of letting them rot in the store.

Phase 3 lesson: the original SHACL DeckShape required exactly 99–100 cards (Commander format). When we added Modern (60+ cards), it broke. The fix wasn't to add format-detection logic to the shape — it was to split into focused shapes: a general DeckShape (any deck must declare its source), a specific CommanderDeckShape (99–100 cards), and ConstructedDeckShape (60+ cards). Each is independently enabled.

How each source becomes triples

SourceAuthFormWhat we extractWhere it lands
Scryfall none Bulk JSON download (~250 MB) oracle_id, name, colors, type_line, prices.{eur,usd}, legalities.commander Default graph (global card facts)
EDHREC none Per-commander JSON page inclusion % (computed from num_decks / potential_decks), synergy, category Named graph per commander (mtg:context/<slug>)
EDHTop16 none GraphQL Commander aggregate stats + per-entry standing/wins/decklist (joined by oracleId) Default graph (tournament facts)
TopDeck.gg API key REST Any format (EDH, Modern, …) with full decklists + win/loss + standings Default graph, with mtg:hasFormat on each tournament + deck
Anthropic Claude API key Messages API (prompt-cached) Natural-language deck suggestions, grounded in graph context Not persisted — used in POST /api/.../ai/suggest
Why "joined by oracleId" matters. Scryfall, EDHTop16, and the Scryfall bulk cache all expose oracle_id. Because we URL-key cards by oracleId (mtg:card/<oracle_id>), tournament decks reference the exact same node as the global card facts. No string-matching, no fuzzy resolution. The triplestore handles the join.

The phase-by-phase journey

Phase 1 — MVP

EDHREC + Scryfall ingestion, ontology, SHACL shapes, GET /api/commanders/{slug}/recommendations with price & inclusion filters, budget deck builder. 4 unit tests. Proved the loop end-to-end.

Phase 2 — Tournament signals (EDHTop16)

GraphQL ingestion of tournament data. New /api/commanders/{slug}/meta endpoint. /recommendations gains source, maxPlacement, minTopCutAppearances filters. Bugs found by going live (and fixed): commander-name slug lookup, HttpClient BaseAddress quirk, Content-Type strictness, GraphQL field-name drift. 4 new tests.

Phase 3 — Multi-format (TopDeck.gg)

One REST API covering EDH + Modern + Legacy + Pioneer + Standard + Pauper + …. Generalised mtg:hasFormat so it works on both Tournament and Deck. Refactored SHACL into focused per-format shapes. Feature-flagged behind a free API key.

Phase 4 — Format endpoints + smarter builder + AI

/api/formats, /api/formats/{format}/meta, /api/formats/{format}/staples, /api/commanders (list). Replaced naive greedy deck builder with a quota-aware two-pass build that respects Commander format conventions (37 lands / 10 ramp / 10 draw / 8 removal / 20 creatures / 14 other). New MtgDeckEngine.Ai project: Anthropic-backed POST /api/commanders/{slug}/ai/suggest with prompt caching on the graph-context block.

Phase 5 — AWS deployment

Documented FusekiGraphRepository's drop-in compatibility with Neptune (same SPARQL 1.1 wire protocol). Added k8s/ (Kustomize base + dev/prod overlays) and deploy/helm/mtg-deck-engine (Helm chart with IRSA, ConfigMap, Secret, HPA, Ingress, nightly CronJob). Added terraform/ with modules for Neptune + envs for VPC/EKS/Neptune/IRSA. Ready to terraform apply + helm install.

AWS deployment in one screen

# 1. Provision the infrastructure
cd terraform/envs/dev
terraform init
terraform apply

# 2. Point kubectl at the new EKS cluster
aws eks update-kubeconfig --name mtg-deck-engine-dev

# 3. Install the AWS Load Balancer Controller (one-time per cluster)
helm repo add eks https://aws.github.io/eks-charts
helm install aws-lb-controller eks/aws-load-balancer-controller \
  --namespace kube-system \
  --set clusterName=mtg-deck-engine-dev \
  --set serviceAccount.create=true

# 4. Deploy the app
helm install mtg deploy/helm/mtg-deck-engine \
  --namespace mtg-deck-engine --create-namespace \
  --set serviceAccount.irsaRoleArn=$(terraform -chdir=terraform/envs/dev output -raw irsa_role_arn) \
  --set sparql.queryEndpoint=https://$(terraform -chdir=terraform/envs/dev output -raw neptune_endpoint):8182/sparql \
  --set sparql.updateEndpoint=https://$(terraform -chdir=terraform/envs/dev output -raw neptune_endpoint):8182/sparql \
  --set-string secrets.topdeckApiKey=$TOPDECK_API_KEY
Why no code change to swap Fuseki → Neptune? Both speak SPARQL 1.1 over HTTP — the wire-level standard. FusekiGraphRepository only knows about POSTing SPARQL to a URL and reading JSON results back. Whether that URL is localhost:3030/mtg/sparql or cluster.us-east-1.neptune.amazonaws.com:8182/sparql doesn't matter to the code. This is the value of writing against a standard.
